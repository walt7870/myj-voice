# 美宜佳语音购物服务接口接入说明

## 1. 接入原则

设备负责拾音、编码、下行解码和 DAC 播放；服务端负责鉴权、IAT、对话、TTS、意图与订单事件转发。服务端不绑定 AC7911BA 或其他具体芯片。

服务根地址：

```text
本地：http://127.0.0.1:8787
公网：https://www.niuwancheng.cn/myj-voice-shop
```

旧路径 `https://www.niuwancheng.cn/mjy-voice-shop` 保留兼容，已下发设备无需立即修改；新接入统一使用 `/myj-voice-shop`。

最短接入顺序：

1. `GET /api/device/config`，读取当前 provider 动态生成的 `audio_profiles`。
2. `POST /api/device/auth`，用 `device_id/device_secret` 换短期 token。
3. 从动态能力中选择 input/output profile，并把四个音频参数写入 WebSocket URL。
4. 使用 `audio_stream_start/chunk/end` 上送音频。
5. 校验每个 `tts_audio_chunk` 的元数据后交给匹配的 decoder。
6. 普通播报在队列彻底排空后恢复拾音；实体按键打断则先本地停播、清队列，再通知服务端并立即恢复拾音。

不要根据文件头、首包内容或芯片型号猜格式；不要在连接中途切档位。旧协议值 `pcm16k` 已废弃并由 `pcm + 独立 rate` 替换。

### 1.1 测试环境快速接入

当前测试环境与公网验收地址一致：

```text
https://www.niuwancheng.cn/myj-voice-shop
```

设备侧联调建议按以下顺序验收：

1. 先访问 `GET /api/health` 和 `GET /api/device/config`，确认公网路由、TLS、动态音频能力可达。
2. 使用已线下配置的真实 `device_id/device_secret` 调 `POST /api/device/auth` 换 token；公网不会接受 `DOLL-0001/demo-secret`。
3. 使用 Python SDK 先跑文本链路，再跑 `--interrupt-after-first-chunk`，确认能收到 `tts_interrupted`，且旧轮不再继续播报。
4. 常驻设备不要因为 `tts_interrupted` 关闭 WebSocket；它只代表当前播报轮次结束，后续业务尾事件和下一轮语音仍在同一连接内继续。
5. C++ demo 仅支持明文 HTTP/WS。直接连公网 HTTPS/WSS 时，需要设备侧集成 TLS/WebSocket 库，或通过可信内网网关把 HTTPS/WSS 转成板端可用的明文连接。

Python 公网文本烟测：

```bash
DEVICE_ID='<已配置设备 ID>' \
DEVICE_SECRET='<独立设备密钥>' \
BASE_URL=https://www.niuwancheng.cn/myj-voice-shop \
SDKs/python/run_text_demo.sh
```

Python 公网按键打断烟测：

```bash
DEVICE_ID='<已配置设备 ID>' \
DEVICE_SECRET='<独立设备密钥>' \
BASE_URL=https://www.niuwancheng.cn/myj-voice-shop \
SDKs/python/.venv/bin/python SDKs/python/device_client.py \
  --base-url "$BASE_URL" --device-id "$DEVICE_ID" --device-secret "$DEVICE_SECRET" \
  --text "请简短介绍一下可口可乐" --play --interrupt-after-first-chunk
```

验收预期：首个可播放 TTS 包到达后本地立即停播，随后收到 `tts_interrupted.payload.status=interrupted` 或幂等状态；旧轮的 `llm_delta/reply_sentence/tts_audio_chunk/voice_done` 不再进入播放器，`latency_metrics`、订单草稿或下单等业务尾事件仍会继续到达。

## 2. 动态能力发现

```http
GET /api/device/config
```

响应中的结构以当前实际响应为准，示意如下：

```json
{
  "audio_profiles": {
    "input": {
      "default": { "format": "mp3", "sample_rate": 16000 },
      "supported": [
        { "format": "mp3", "sample_rates": [16000] },
        { "format": "pcm", "sample_rates": [16000] }
      ]
    },
    "output": {
      "default": { "format": "mp3", "sample_rate": 16000 },
      "supported": [
        { "format": "mp3", "sample_rates": [8000, 16000, 24000] },
        { "format": "pcm", "sample_rates": [16000] }
      ]
    },
    "query": ["in_format", "in_rate", "out_format", "out_rate"],
    "pcm": { "bit_depth": 16, "channels": 1, "endianness": "little" },
    "packetized": {
      "opus": { "one_packet_per_chunk": true, "frame_duration_ms": 20 },
      "speex": { "one_packet_per_chunk": true, "quality": 7, "frame_duration_ms": 20 }
    }
  }
}
```

示例列表不是静态承诺。格式值和 rate 合法，只表示协议可解析；是否被当前 IAT/TTS provider、方向、账号开放，必须以本次 `audio_profiles.input/output.supported` 为准。客户端启动时读取一次，收到 profile 类错误后应重新读取；不能把文档矩阵硬编码成服务端能力。

## 3. 鉴权

```http
POST /api/device/auth
Content-Type: application/json

{"device_id":"<已线下配置的设备 ID>","device_secret":"<该设备的独立密钥>"}
```

成功响应：

```json
{"token":"短期 token","expires_at":1780000000}
```

token、设备密钥和讯飞签名 URL 不得进入日志。生产设备必须使用线下配置的独立密钥，并在 token 到期前刷新。`GET /api/device/config` 只返回字段占位说明，不下发任何可用设备凭据。

`DOLL-0001 / demo-secret` 仅用于服务器本机、本地开发机或 SSH 隧道调试；公网代理请求无法用它换 token，预签的 DOLL token 也无法升级设备 WebSocket。

## 4. WebSocket 四参数

```text
/api/device/voice?device_id=...&token=...&in_format=...&in_rate=...&out_format=...&out_rate=...
```

| 参数 | 值 | 默认 | 含义 |
| --- | --- | --- | --- |
| `in_format` | `mp3/pcm/opus/speex` | `mp3` | 设备上行格式 |
| `in_rate` | `8000/16000/24000` | `16000` | 上行采样率 Hz |
| `out_format` | `mp3/pcm/opus/speex` | `mp3` | TTS 下行格式 |
| `out_rate` | `8000/16000/24000` | `16000` | 下行采样率 Hz |

四参数在一条连接的完整生命周期内固定。切换任一参数必须关闭旧连接并重新握手。Speex 没有 24k 档位；profile 还要经过方向/provider 能力校验。

浏览器体验页固定使用：

```text
/api/chat/voice?in_format=pcm&in_rate=16000&out_format=mp3&out_rate=16000
```

## 5. provider 方向矩阵

下表是协议实现和讯飞官方参数形成的候选矩阵，用于解释边界，不代表当前账号已逐项实测。对外能力始终以动态配置为准；Opus/Speex 必须在当前端点、账号、设备 decoder 上验证原生包边界后才能开放。

| 方向/provider | MP3 | PCM | Opus | Speex |
| --- | --- | --- | --- | --- |
| 超拟人/私有 IAT 候选 | 16k | 16k | 不开放 | 不开放 |
| 标准 IAT 候选 | 8k/16k | 8k/16k | 官方未声明输入能力，不开放 | 8k/16k |
| 超级拟人 TTS 候选 | 8k/16k/24k | 16k | 需实测，默认不开放 | 需实测，默认不开放 |
| 标准 TTS 候选 | 8k/16k | 8k/16k | 8k/16k | 8k/16k |

关键边界：

- 8k、16k、24k 是离散档位，不支持任意采样率。
- Speex 仅 8k/16k。
- 标准 IAT 无 Opus input；不能从标准 TTS 的 Opus output 能力反推上行能力。
- 24k 仅在某些 TTS MP3 档位可能存在；浏览器和 SDK 默认仍为 16k，客户端不得硬猜 24k。
- 讯飞标准 TTS 对应参数包括 `aue=raw/lame/opus/opus-wb/speex-org-*` 与 `auf=audio/L16;rate=8000/16000`；实际字段由服务端 provider adapter 构造。

## 6. 线级音频和分包

所有音频均放在 JSON `audio` 字段内，以标准 base64 传输；不加 data URL 前缀，不使用 WebSocket binary frame。

### 6.1 PCM

- signed 16-bit little-endian（S16LE）、mono、无 RIFF/WAV 头。
- 采样率取连接方向对应的 rate。
- 一个完整采样为 2 bytes，包长度必须为偶数。
- 推荐 20-40ms；40ms 大小为 `rate * 2 * 40 / 1000` bytes，例如 16k 为 1280 bytes。

### 6.2 MP3

- 连续编码字节流，按编码器产出顺序发送。
- 不要求每个 chunk 是独立 MP3 文件；不要每片重复 ID3 头。
- 可按合理字节块切连续文件，但不能重排、补包或让服务端猜码率。

### 6.3 Speex

- 必须是标准开源 Speex quality 7 的预编码数据，SDK/服务端不负责 PCM 编码。
- 每个 `audio_stream_chunk` 恰好一个 20ms 包。
- 8k 窄带每包 38 bytes；16k 宽带每包 60 bytes。
- 不能把多个包拼成一个 chunk，也不能拆包。

### 6.4 Opus

- 每个 `audio_stream_chunk` 恰好一个完整的设备编码包。
- 包长可变；普通 raw 文件若没有长度前缀/packet table 就无法恢复边界。
- Python/C++ demo 因此明确拒绝 Opus 平面文件上行。真实设备应直接从 encoder callback 得到一个包并发一个 chunk。
- 本协议不引入 Ogg 容器。

### 6.5 服务端透明边界

服务端不解码、不编码、不转码、不重采样、不封装 Ogg、不为凑时长缓存或聚合压缩包。它只做 Base64、空包、大小、格式特定包长和事件顺序校验，并保持 native bytes、包边界和顺序。

## 7. 客户端事件

```json
{"type":"audio_stream_start","conversation_id":"device-1","trace_id":"trace-1","client_sent_ms":1780000000000}
```

```json
{"type":"audio_stream_chunk","audio":"base64 audio bytes"}
```

```json
{"type":"audio_stream_end","conversation_id":"device-1"}
```

播报期间实体按钮完成消抖后，使用当前已收到的播放轮次发送独立控制事件；不得伪造 `turn_id`，也不得把按钮转换为音频或文字：

```json
{"type":"tts_interrupt","conversation_id":"device-1","turn_id":"turn-1","source":"button"}
```

`conversation_id` 与 `turn_id` 必须属于当前 WebSocket，`source` 本期只接受 `button`。该事件不进入 IAT、不会形成新的用户消息或订单意图。

PCM/MP3 还可用整段 `audio_segment`；Opus/Speex 是 packetized codec，必须走 stream，避免整段事件丢失包边界。文本联调不需要音频文件：

```json
{"type":"text","conversation_id":"device-1","text":"我要一瓶可口可乐"}
```

## 8. TTS 元数据和 decoder

```json
{
  "event_type": "tts_audio_chunk",
  "conversation_id": "device-1",
  "turn_id": "turn-1",
  "payload": {
    "audio": "base64 audio bytes",
    "seq": 0,
    "is_last": false,
    "format": "mp3",
    "sample_rate": 16000,
    "channels": 1
  }
}
```

PCM 事件额外包含 `"bit_depth":16`。客户端收到每个事件都必须验证：

1. `format/sample_rate` 与连接的 output profile 完全一致。
2. `channels=1`；PCM 还要验证 `bit_depth=16`。
3. `seq/is_last` 满足本轮顺序。
4. metadata 不匹配时停止该轮播放并报告协议错误，不能硬猜采样率或换 decoder。

MP3/PCM 可进入对应播放器。Speex 固定长包可保存为 raw 流；Opus 可变长包必须保留边界，Python/C++ demo 的 `.opuspack` 使用 `uint32 little-endian 长度 + 包字节`，它不是 Ogg/Opus 容器，不能直接播放。板端应按每个 `tts_audio_chunk` 实时送入 decoder。

Opus/Speex 下行时，服务端只发送真实的完整 packet，不使用空 `tts_audio_chunk` 表示结束。服务端最多延后一个完整 packet；收到后续 packet 时立即释放前一个，收到上游 final 时将 `is_last=true` 标在最后一个真实 packet 上。若压缩流从始至终没有任何真实 packet，或 final 时仍有残缺 packet，服务端返回 TTS 错误而不会伪造空包。MP3/PCM 继续保持原有连续字节流和空 final 语义。

不同 `seq` 可因多句并行合成而交错到达。客户端必须在同一 `turn_id` 内按 seq 播放/落盘：首个 seq 仍可流式播放，后续 seq 在前序列放行前只能预缓冲。不同 turn 的相同 seq 不得共用缓冲。

### 8.1 按键打断确认与业务尾

合法控制事件返回：

```json
{
  "event_type": "tts_interrupted",
  "conversation_id": "device-1",
  "turn_id": "turn-1",
  "payload": {
    "source": "button",
    "status": "interrupted"
  }
}
```

`payload.status` 的完整语义：

| status | 含义 | 设备处理 |
| --- | --- | --- |
| `interrupted` | 服务端首次接受该轮打断 | 保持本地停播，继续当前连接 |
| `already_interrupted` | 同一轮已被打断 | 幂等确认，不重启旧播放器 |
| `already_finished` | 该轮服务端生产已结束 | 保持本地当前状态，不补播旧音频 |

未知 `turn_id`、跨会话轮次、缺少字段或 `source` 不是 `button` 时返回 `error.code=bad_request`，且不得影响其他轮次。

被打断轮次不再发送普通 `voice_done`。`tts_interrupted` 只终止回复/播放侧；已经启动的商品与订单分析不取消，`intent_analysis`、`product_matches`、`order_draft`、`order_created`、`order_refunded`、`analysis_done`、`latency_metrics` 等业务尾事件仍可在确认之后到达。设备必须继续消费这些事件，不能收到确认就关闭 WebSocket。服务端会停止继续读取旧轮 LLM delta、终止该轮 TTS producer 并过滤尚未发出的 `llm_delta`、`reply_sentence`、`tts_audio_chunk`、`voice_done`；provider 任务也会在取消或超时后主动收敛，不作为后台悬挂任务继续占用轮次容量。

同一连接可以在本地停播后立即发送下一次 `audio_stream_start/chunk/end`。新轮获得新的 `turn_id`，正常以 `voice_done` 结束；同一 `conversation_id` 的业务分析与订单写动作仍按轮次顺序提交，按键打断不会改变订单先后关系。

## 9. 播报与拾音状态机

为了避免扬声器回声重新进入 IAT，TTS 不可打断配置生效时，播报相关阶段全部禁止上送麦克风音频。实现必须使用同一个门控条件同时控制提交和 UI。
播放队列的最后一段音频触发 `ended` 后，浏览器端立即清除 TTS 拾音锁并更新 UI，不再设置额外固定延迟。体验页对话区最多保留 100 条当前轮消息，默认跟随最新消息；用户主动向上滚动后保留其查看位置。

只有以下条件全部为真，才可发送 `audio_stream_chunk`，且页面才可显示“可拾音/正在聆听”或麦克风动画：

- 麦克风 permission 已 granted。
- capture 已 active。
- WebSocket 已 OPEN。
- 当前业务策略允许 pickup。
- 不在发送锁/打断检查锁中。
- 没有 TTS prebuffer、待播队列或正在播放的播放器。
- TTS 静音保护和播放结束后的安全延时已解除。

收到首个 TTS chunk 时，如果已有上行 stream，应立即结束/丢弃当前录音窗口，此后不得提交麦克风 chunk。`voice_done` 只代表服务端本轮生产结束，不代表扬声器播放结束；队列未排空时 UI 不能提前恢复。播放器 `ended/error`、所有队列与 prebuffer 清空、策略仍允许时，才恢复拾音状态。

实体按键是播报期间恢复拾音的独立控制路径，必须按以下顺序实现：

1. GPIO ISR 只完成消抖并通过 ISR-safe queue/notification 向音频/网络 owner task 投递 `BUTTON_INTERRUPT`；ISR 内不得进行 WebSocket、decoder、DAC、动态内存或锁操作。
2. owner task 串行记录当前 `conversation_id + turn_id`，先停止 decoder/DAC，清空 DMA/I2S、预缓冲、乱序 seq 和软件播放队列。
3. 将 pair 放入最多保留 64 项的 interrupted 集合。后续相同 pair 的 `llm_delta`、`reply_sentence`、`tts_audio_chunk`、`voice_done` 必须在 base64 解码和 seq 校验前丢弃；不能使用“忽略所有 TTS”的全局标志，以免误丢下一轮。
4. 通过原 WebSocket 发送 `tts_interrupt`。网络发送失败不回滚本地停播，也不循环补发旧轮控制事件。
5. 播放链路确认排空后立即回到 `LISTENING` 并允许下一轮上行，不等待服务端 ack，也不增加固定 500ms 延时。若实机存在声学拖尾，只配置实测所需的最短板端 guard time。

按钮与最后一个 TTS 包可能同时到达，二者必须由同一个 owner task 串行处理；无论先后顺序，最终状态都是旧轮队列为空且可拾音。重复按钮或没有活跃播报时为 no-op。

暂停、断线、权限未给、等待播放器排空和 TTS prebuffer 阶段均不可显示可拾音。不要为了支持打断而常开回声拾音；既有“不打断”语义保持不变。

浏览器体验页的普通断句由 `silenceMs` VAD 触发，同时从首次有效语音起设置独立的 `maxSpeechMs=10000` 硬截止。硬截止不依赖后续 `AudioProcess` 回调，持续背景声或回调调度异常都不能让单句无限延长。

## 10. AC7911BA 建议

推荐先使用：

```text
in_rate=16000&out_rate=16000
```

具体 format 从动态能力和固件已启用 decoder/encoder 中选择。设备收到压缩下行后，在 DAC 前完成解码，转换为板端音频链路要求的 16kHz、16bit、mono PCM。推荐档位属于设备接入建议，不会写死进服务端；其他芯片可选择动态配置公开的 8k/24k 档位。

### 10.1 当前嵌入式 demo 的 P0 低延迟参数

`client/voice_shop_demo.c` 当前采用一版不改变服务端协议的过渡优化：

| 项目 | 调整前 | 当前值 | 目的 |
| --- | ---: | ---: | --- |
| PCM 聚合 | 5 × 40ms = 200ms | 2 × 40ms = 80ms | 更早提交有效语音，同时避免同步 WSS 每秒发送 25 次 |
| WSS 运行期读切片 | 500ms | 20ms | 缩短共享 mbedTLS context 下发送方等待读锁的时间 |
| 松键尾部 | 活跃采集下最多追赶 60 帧/2.5s | 先停采集，再按快照最多补 3 帧/120ms | 防止 `audio_stream_end` 追赶仍在增长的环缓 |
| MP3 流式起播 | 12KB | 4KB | 降低首个 TTS chunk 到实际出声的等待 |

该版本仍是“同一个 mbedTLS context + 收发互斥”的过渡实现。20ms 读切片保证现有帧顺序和同步发送语义，最终架构仍建议改成单 I/O owner：其他任务只投递 TX 队列，由同一网络任务串行执行 TLS read/write。

松键优化依赖板端 `_device_net_audio_recorder(false)` 停止生产者后不清空尚未读取的录音环缓。烧录后必须核对 `pending/target/sent/dropped_est` 日志及句尾识别完整性；若句尾被截断，先把 `VOICE_SHOP_TAIL_MAX_FRAMES` 回退到 5（200ms），不要恢复活跃生产者下的无界追赶。

本次 6.22s 样本中，设备端可直接优化的主要部分是 713ms 松键提交和 1.27s TTS 本地缓冲/开播。按同一网络条件估算，P0 固件目标是把松键到 end 压到约 150–300ms、首个 TTS chunk 到出声压到约 450–700ms，整链路约 4.8–5.2s。此处是基于单次日志的预算，不是烧录实测；若要稳定接近 3s，还需把约 3.1s 的云端 ASR final 阶段进一步压缩。

### 单会话连续订单语义

同一个 `conversation_id` 可以连续创建多张订单。服务端将成功的 `order_created` 视为购物车边界：边界之后识别到的新商品只进入下一张订单，不继承已创建订单中的商品。确认词优先于同句中的泛化结束词，例如“不要了，直接下单吧”应产生 `confirm_order` 和新的 `order_created`，不得产生 `conversation_ended`。设备端无需为第二张订单主动创建新会话，但仍可由用户明确开启“新一轮”。

## 11. 错误处理

握手阶段 HTTP 400，不创建上游连接：

| code | 条件 |
| --- | --- |
| `unsupported_audio_format` | format 不是四个协议值 |
| `unsupported_audio_rate` | rate 不是 8000/16000/24000，或 Speex 使用 24000 |
| `unsupported_audio_profile` | format/rate 合法，但当前方向/provider 未开放组合 |

连接建立后的错误事件：

| code | 条件 | 客户端处理 |
| --- | --- | --- |
| `invalid_audio_packet` | Base64、空包、奇数 PCM、Speex 包长、超限或顺序非法 | 停止本轮上行并修复 packetizer |
| `upstream_audio_profile_rejected` | 讯飞运行时拒绝当前 profile | 记录 provider/方向/profile/上游码，重新读取 config；不静默降级 |
| `asr_failed` | IAT 本轮失败 | 结束录音窗口，可提示重试 |
| `tts_failed` | TTS 本轮失败 | 清空该 turn 播放队列，可展示文字回复 |
| `bad_request` | `tts_interrupt` 缺字段、来源非法、轮次未知或会话不匹配 | 保持本地停播结果，不影响其他轮次；修正状态机身份跟踪 |

日志不得包含音频正文、完整 token、device_secret 或签名 URL。

## 12. 延迟与可观测性

服务端透明转发指标：

```text
voice_audio_uplink_relay_duration
voice_audio_downlink_relay_duration
```

指标按 provider、format、sample_rate 标记，分别测量完整事件收到至提交上游、上游包收到至提交客户端。压缩档位与 MP3 基线做 A/B 时，目标是服务端 P95 转发开销相对增加不超过 2ms，且检查中不能出现多包累计后一次发送。播放器预缓冲（例如浏览器 MP3 约 4KB）属于客户端播放策略，不得回流成服务端聚合。

体验页链路诊断使用一条常驻 WebSocket，避免每轮重新握手时丢失首个 `audio_received`。流式 PCM 轮次额外展示 `audio_input_done` 和实际 `audio_duration_ms`；用 `audio_input_done -> asr_done` 判断讯飞收尾耗时，用 `speech_sent -> audio_input_done` 判断客户端录音是否拖长。

IAT 的 `ws[].cw` 是同一分段的候选列表，服务端只采用第一个首选候选，不能把所有候选拼接成用户文本。动态分片仍按先后顺序合并，ASR partial 只用于展示，业务处理等待 ASR final。

浏览器体验页发送 `audio_stream_end` 或 `audio_segment` 后，若 8 秒内未收到 ASR final/错误/忽略事件，会自动解除发送锁并恢复拾音。服务端单个实时 IAT 会话最长 20 秒，超时返回“语音识别超时，请再说一遍”；客户端应将该错误视为可重试，不应终止后续语音会话。

嵌入式 demo 烧录后至少采集以下日志并计算 P50/P95，不能只用一次体感判断：

- `ptt stop t` → `end timing t/total`：松键到 `audio_stream_end` 完成。
- `ws tx wait/write`：共享 TLS mutex 等待和实际 socket 写耗时；只有任一阶段达到 20ms 才输出。
- `mp3 first chunk t` → `mp3 speaking t/first_to_speak`：下行首包到 DAC 开始播放。
- ASR final、首句 reply、首个 TTS chunk 的服务端事件时刻：与设备日志对齐后拆分云端和本地预算。

验收时同时观察 `chunk_fail`、WebSocket 重连、MP3 decoder error、卡顿/欠载和句尾识别。4KB 出现欠载时可按 6KB、8KB 逐级回退；不要直接恢复 12KB 而不记录对照数据。

## 13. Python/C++ 完整命令

Python 文本：

```bash
SDKs/python/.venv/bin/python SDKs/python/device_client.py \
  --base-url http://127.0.0.1:8787 --text "我要一瓶可口可乐" \
  --in-format mp3 --in-rate 16000 \
  --out-format mp3 --out-rate 16000 --output /tmp/python-reply.mp3
```

Python PCM：

```bash
SDKs/python/.venv/bin/python SDKs/python/device_client.py \
  --base-url http://127.0.0.1:8787 --audio /tmp/input.pcm --stream \
  --in-format pcm --in-rate 16000 \
  --out-format mp3 --out-rate 16000 --output /tmp/python-reply.mp3
```

C++ 文本：

```bash
SDKs/cpp/device_client --host 127.0.0.1 --port 8787 \
  --text "我要一瓶可口可乐" \
  --in-format mp3 --in-rate 16000 \
  --out-format mp3 --out-rate 16000 --output /tmp/cpp-reply.mp3
```

C++ PCM：

```bash
SDKs/cpp/device_client --host 127.0.0.1 --port 8787 \
  --audio /tmp/input.pcm --in-format pcm --in-rate 16000 \
  --out-format mp3 --out-rate 16000 --output /tmp/cpp-reply.mp3
```

text mode 不需要 `--audio`。SDK 不编码 PCM 到压缩 codec；Speex/Opus 输入必须由设备 codec 预编码并保留包边界。

模拟首个可播放分片后按下实体按钮：

```bash
SDKs/python/.venv/bin/python SDKs/python/device_client.py \
  --base-url http://127.0.0.1:8787 --text "我要一瓶可口可乐" --play \
  --interrupt-after-first-chunk

SDKs/cpp/device_client --host 127.0.0.1 --port 8787 \
  --text "我要一瓶可口可乐" --interrupt-after-first-chunk
```

两套 demo 都会本地先停播，等待 `tts_interrupted` 与 `latency_metrics` 业务尾后结束单轮演示；常驻固件不应结束 WebSocket，而应立即开始下一轮拾音。

本仓库没有真实开发板 GPIO、按键消抖、decoder、DAC、DMA/I2S HAL 源码。这里交付的是服务端协议、取消边界和 Python/C++ 状态机参考；实际管脚接线、ISR-safe 投递与硬件静音时延必须在板端固件仓库实现并烧录验收。
