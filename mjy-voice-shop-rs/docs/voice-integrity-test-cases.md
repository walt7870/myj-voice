# 录音播报完整性测试用例

## 验收目标

验证体验页与设备从持续录音、ASR 转写、LLM 回复、TTS 合成到本地播报的完整链路稳定可用，重点确保普通播报期间停止拾音、实体按键能本地立即停播并恢复下一轮、页面状态与真实拾音能力一致、长文本播报不卡顿，并且异常短音频不会污染对话区。

## 自动化回归

执行前先启动本地服务：

```bash
scripts/start-dev.sh
```

执行完整回归：

```bash
npm run voice:check
npm run ui:check
cargo test
SDKs/python/.venv/bin/python SDKs/python/protocol_self_test.py
SDKs/cpp/build.sh
SDKs/cpp/device_client --self-test
```

`npm run voice:check` 覆盖以下断言：

| 用例 | 操作 | 通过标准 |
| --- | --- | --- |
| 测试钩子可用 | 以 `?voiceTest=1` 打开体验页 | 页面暴露语音链路测试 API，控制台无错误 |
| 播报静音配置生效 | 读取体验页当前配置 | 播报静音固定开启，用户不能在体验页关闭 |
| TTS 小包预缓冲 | 注入首个 256 bytes TTS 分片 | 不立即创建音频播放，避免小包边下边播造成卡顿 |
| TTS 达阈值开播 | 继续注入超过预缓冲阈值的分片 | 只启动 1 次播放，不重复创建播放器 |
| 空 ASR 抑制 | 注入“没有识别到有效语音”错误事件 | 不在聊天气泡里显示该提示 |
| 旧打断事件兼容 | 播放中注入旧协议打断命中事件 | 当前播报停止，后续同一轮旧 TTS 分片被忽略 |
| 播报中录音门控 | 模拟 TTS 播报期间收到高能量音频帧和 `voice_done` | 不发送普通或打断检测音频；状态区和麦克风按钮仍显示“播报中，暂停收音” |
| 拾音状态矩阵 | 逐一翻转权限、capture、WS、pickup 策略、发送锁、TTS prebuffer、播放队列、播放器状态 | 只有所有前置条件同时满足时 `canCaptureAudio` 为 true，UI 派生状态使用同一结果 |
| TTS 元数据拒绝 | 注入与固定浏览器 profile 不一致的 MP3/24k 分片 | 不创建播放器，安全提示期望 `mp3/16000`，不按 24k 猜测播放 |

设备按键协议自动化还需覆盖：

| 用例 | 操作 | 通过标准 |
| --- | --- | --- |
| 本地优先停播 | 在首个可播放 `tts_audio_chunk` 后调用 `interrupt_tts_from_button` | decoder/player stop 与队列清空先于发送控制帧；发送失败也不恢复旧音频 |
| 精确身份与迟到过滤 | 打断一个 `conversation_id + turn_id` 后注入该 pair 的迟到回复/音频/`voice_done`，再注入新 pair | 旧 pair 在 base64 解码和 seq 校验前丢弃；新 pair 正常播放 |
| 幂等与有界状态 | 对同一轮重复按钮，并连续记录超过 64 个被打断轮次 | 同一轮只停播/发包一次；interrupted 缓存最多 64 项且不误伤新轮 |
| 服务端取消收敛 | 在 LLM、标准 TTS、标准 TTS fallback 和超拟人流中途触发取消 | 不再产生旧轮 reply/TTS/`voice_done`，provider 任务主动终止，不长期占用完整轮次容量 |
| 同连接业务保留 | 首轮打断后不关闭 WebSocket，继续读取业务尾并发起第二轮 | 首轮仍有订单/分析尾事件；第二轮收到新 `turn_id`、ASR 和正常 `voice_done` |

## 人工验收用例

| 编号 | 场景 | 前置条件 | 操作 | 通过标准 |
| --- | --- | --- | --- | --- |
| V01 | 基础一轮对话 | 打开体验页 | 点击开始持续监听，说“我要一瓶可口可乐” | 用户话术识别正确，模型回复出现，TTS 开始播报，链路诊断有 `转写完成`、`模型首字`、`TTS 首包`、`开始播报` |
| V02 | 长文本播报流畅性 | 使用较长回复 prompt | 让模型输出 80 字以上播报内容 | 播报从首包后连续播放，中间无明显停顿；链路诊断中 `TTS 首包` 到 `开始播报` 不异常拉长 |
| V03 | 回声规避 | 扬声器外放，麦克风正常开启 | 在 TTS 播报期间不说话 | 不新增用户消息，不触发新的 ASR 结果，不出现“读取播报内容继续对话”的回声循环 |
| V04 | 播报期间硬静音 | TTS 正在播报 | 对麦克风说任意内容 | 不产生普通 ASR 或打断检测请求，页面持续显示“播报中，暂停收音” |
| V05 | 异步状态防穿透 | TTS 正在播报 | 等待本轮 `voice_done` 或空 ASR 事件到达 | 页面不能提前显示“持续监听中”或“继续监听” |
| V06 | 播报结束后恢复收音 | 持续监听中完成一次播报 | 播报结束后立即说“再来一瓶雪碧” | 最后一段音频 `ended` 后同一事件循环内恢复拾音与可监听状态，不需要手动重开麦克风 |
| V07 | 短促噪声过滤 | 持续监听中 | 轻敲桌面或发出 0.5 秒以内短音 | 不出现“没有识别到有效语音，请再说一遍”的聊天气泡 |
| V08 | 连续多轮稳定性 | 持续监听中 | 连续完成 10 轮下单/查询/闲聊 | 页面不卡死，语音播放不重叠，链路诊断可滚动查看最新阶段 |
| V09 | 退单防误触 | 已成功下单 | 依次说“让玩偶退下”“退单”“不要退单” | 均不触发退单接口 |
| V10 | 明确退单 | 已成功下单 | 说“我要退单”或“帮我取消订单” | 才触发退单接口并结束本轮对话 |
| V11 | 权限/断线状态 | 先拒绝麦克风权限，再授权后让 WebSocket 断开 | 分别显示权限等待和连接未就绪；两个阶段都无监听动画、无音频上送 |
| V12 | 队列排空边界 | TTS 已收到 `voice_done`，但播放器还有待播内容 | 播放队列、prebuffer 和当前 Audio 全部结束前不得显示“持续监听中” |
| V13 | 结束交互 ASR 变体 | 持续监听中 | 说“退下吧”，并注入识别结果“退一下吧” | 只显示一次用户文本，固定回复“好的主人，我退下了。”；收到 `conversation_ended` 后麦克风停止，TTS 收尾不得覆盖“对话已结束”；不得触发或声称退单 |
| V14 | 单句硬截止 | 持续背景声高于 VAD 阈值 | 持续说话或播放背景声超过 10 秒 | 最迟 10 秒触发 `audio_stream_end`，不能继续累积为 20 秒以上单句 |
| V15 | ASR 收尾超时恢复 | 持续监听中，模拟服务端收到 `audio_stream_end` 后不返回 final | 说完一句后等待 8 秒 | 页面不再长时停在“ASR 收尾中”；显示“识别超时，请再说一遍”并恢复拾音，无需手动刷新或重开麦克风 |
| V16 | 对话历史滚动 | 对话区已有 20 条以上消息 | 向上滚动查看历史，期间接收新消息 | 消息区独立纵向滚动，至少保留 20 条；用户不在底部时新消息不强制拉回底部 |
| V17 | 单会话连续下两单 | 持续使用同一个 conversation | 说“我要一瓶可口可乐”并确认；再说“我还要一杯纯牛奶”“不用了，直接下单吧” | 生成两张独立订单；第二张草稿和订单只含纯牛奶；末句识别为 `confirm_order`，不得产生 `conversation_ended` |
| V18 | 播报中实体按键停播 | 设备正在 TTS prebuffer 或播放，owner task 已接管按键事件 | 按一次实体按钮 | decoder/DAC 与所有待播队列立即停止/清空；只发送一次 `tts_interrupt`；无需等待 ack 即恢复可拾音，旧语音不复活 |
| V19 | 最后一包并发与重复按钮 | 按钮和最后一个 TTS 包同时到达，并模拟按键抖动 | 连续触发两次按钮事件 | owner task 串行收敛为空队列和 `LISTENING`；只处理一次，不发生旧轮 `voice_done` 穿透或新播放器误停 |
| V20 | 打断后立即下一轮 | 同一 WebSocket 和 conversation 保持连接 | 播报中按键后立刻说“再来一瓶水” | 不重连、不再次按键；下一轮获得新 `turn_id`，能收到 `asr_final`、正常 TTS 和 `voice_done` |
| V21 | 确认播报打断但订单继续 | 第一张订单确认播报正在进行 | 按键后立即发起第二次购买请求 | 第一轮返回 `tts_interrupted` 且不再有旧轮 `voice_done`；第一轮 `order_created/analysis_done/latency_metrics` 仍完成，随后第二轮 `asr_final`、`order_draft` 和 `voice_done` 正常到达；同一 conversation 内第一轮 `order_created` 先于第二轮 `order_draft` |
| V22 | 控制帧发送失败 | 本地正在播报，模拟 WebSocket 写失败 | 按实体按钮 | 本地仍立即静音并恢复拾音，不恢复旧队列、不循环发送旧轮控制事件；连接按既有有界重连策略处理 |
| V23 | 20 次连续打断 | 设备可稳定复用同一长连接 | 连续完成 20 次“开始播报→按键→立即下一轮” | 无旧播报复活、无播放重叠、无重连风暴；记录按键到 DAC 静音、恢复拾音和服务端停止输出的 P50/P95 |

## 卡顿判定标准

| 指标 | 通过标准 | 观察位置 |
| --- | --- | --- |
| 首包前等待 | `TTS 首包` 可出现，但未达到预缓冲阈值前不开始播放 | `链路诊断` |
| 开始播报 | `开始播报` 只出现一次，不反复刷新 | `链路诊断` |
| 播放连续性 | 长文本播报时无连续多次停顿、重启或重叠 | 听感 + 控制台 |
| 回声抑制 | 播报期间无普通 ASR 事件进入对话 | 聊天区 + `voice:check` |
| 状态一致 | 只有拾音门控解除后才显示“持续监听中” | 状态区 + 麦克风按钮 + `voice:check` |
| ASR 收尾 | `音频输入结束` 到 `转写完成` 单独可见，PCM 行展示实际音频时长 | `链路诊断` |
| 按键停播 | 按键到 DAC 静音和恢复拾音不依赖服务端 ack，不叠加固定 500ms | 板端 owner task 日志 + 听感 |
| 打断后资源收敛 | 服务端确认后旧轮无 reply/TTS/`voice_done`，完整轮次容量可回收 | WebSocket 事件 + 服务端测试/日志 |

## 问题定位顺序

1. 先跑 `npm run voice:check`，确认前端播放队列、预缓冲、硬静音和状态一致性没有回归。
2. 再跑 `npm run ui:check`，确认体验页左侧滚动和链路诊断布局没有遮挡。
3. 最后跑 `cargo test`，确认退单严格意图、后端协议、ASR 空结果抑制和 TTS 解析逻辑没有回归。
4. 设备按键异常先运行 Python/C++ self-test，再核对 ISR 是否只投递事件、owner task 是否先停播后发包，以及迟到过滤是否使用完整 `conversation_id + turn_id`。
5. 如果只有人工听感卡顿，优先查看 `链路诊断` 中 `TTS 首包`、`开始播报`、`TTS 首包 bytes` 和网络控制台；若首包间隔正常但听感卡顿，重点排查前端播放器队列和分片大小。

本仓库的自动化只能验收 Rust 服务与 Python/C++ 参考状态机；V18-V23 中真实按钮、GPIO ISR、DAC/DMA/I2S 静音和 P50/P95 必须在包含板端 HAL 的固件仓库及实机上执行，不能用本机 demo 结果代替。
