# 同一对话多订单与退单选择设计

日期：2026-07-29
状态：已与用户确认，待实现

## 1. 背景与问题

当前订单分析逻辑把“同一对话已有一个有效订单”作为禁止再次下单的条件。因此，用户在同一段对话里完成第一次下单后，即使又选择了新商品并再次确认，系统也不会创建第二笔订单；语言模型仍可能回复“订单已下发”，造成回复和数据库事实不一致。

当前退单逻辑只查找最近一个有效订单并立即退款，无法处理同一对话存在多个有效订单时的选择和二次确认。

## 2. 目标

1. 同一对话中，每次独立的购买确认都创建一笔新订单和新的订单号。
2. 新订单只包含上次成功下单之后形成的购物草稿，不能混入旧订单商品。
3. 用户明确要求退单时：
   - 只有一笔有效订单，直接执行退单；
   - 有多笔有效订单，必须先确定目标并再次确认；
   - 默认向用户询问最近的一笔订单；
   - 即使用户已经通过商品名或订单号指定目标，也仍需二次确认。
4. 系统回复必须由确定性的订单动作结果驱动，禁止在没有真实 `order_created` 或 `order_refunded` 结果时宣称成功。
5. 待确认退单状态需要跨进程重启恢复。

## 3. 非目标

- 不在体验页增加按钮或触屏选单交互，保持纯语音/文字对话流程。
- 不改变后台人工退单 API 的既有用法。
- 不放宽现有退单意图安全边界；“退下”“退出”、裸词“退单/退款”及否定表达仍不能直接触发退单。
- 不在本次需求中调整外部订单 MCP 的业务合同。

## 4. 核心模型

### 4.1 有效订单

按对话汇总所有已成功创建的订单，排除状态为已退款、已取消或已关闭的订单。列表按创建时间倒序排列，第一笔为“最近订单”。

查询不能再采用“遇到最近一次退款事件就认为整个对话没有有效订单”的单值逻辑。需要按订单号分别归并创建和退款结果，确保退掉一笔后其他订单仍然有效。

### 4.2 当前购物草稿

当前购物草稿的起点是该对话最近一次成功 `order_created` 事件之后。商品识别只使用这个边界之后的用户输入和草稿事件。

成功创建订单后，当前草稿自然进入下一段；已有有效订单不再阻止新草稿和新订单创建。订单提交失败时不推进边界，用户可以继续确认或修改当前草稿。

### 4.3 待确认退单

使用数据库事件持久化退单选择状态，不增加进程内会话状态。事件至少包含：

- 对话 ID、轮次 ID；
- 候选有效订单号列表；
- 当前待确认订单号；
- 订单摘要、创建时间；
- 状态：等待确认、已替换目标、已确认、已取消、已完成或失败。

读取状态时以同一对话最新的未终结退单选择事件为准。服务重启后，下一轮仍可继续处理“确认”“不是”等回答。

意图判定必须优先处理未终结的待确认退单，再处理普通的确认下单。这样用户在退单确认阶段回答“是的”时，只会确认退单目标，不会误创建新订单。

## 5. 下单流程

1. 用户提出新购买需求，系统从当前草稿边界之后识别商品。
2. 系统播报草稿并询问是否确认下发。
3. 用户给出明确肯定表达后，系统调用订单接口。
4. 只有接口真实成功时才记录 `order_created`、播报新订单号并推进草稿边界。
5. 用户继续购买时形成新草稿；再次确认必须再次调用接口，并得到不同订单号。

若接口失败，记录 `order_failed` 并播报失败，不得生成或复用旧订单号，也不得宣称订单已经下发。

## 6. 退单流程

### 6.1 无有效订单

用户明确提出退单时不调用接口，提示当前没有可退订单。

### 6.2 只有一笔有效订单

用户明确提出退单时直接调用退单接口。成功后记录该订单的退款结果并结束本轮交互；失败时保留订单有效状态并播报失败。

### 6.3 有多笔有效订单

首次收到明确退单请求时不调用退单接口：

- 若请求未指定目标，选择最近订单作为默认待确认目标；
- 若请求包含唯一可识别的商品名或订单号，选择对应订单；
- 若同一种商品匹配多笔订单，选择其中最近一笔，并通过商品、创建时间和订单号尾号帮助用户区分；
- 无论目标如何选出，都播报目标并询问“确认退这一单吗？”。

后续回答：

- “对的、确认、是的”等肯定表达：仅退款当前待确认订单；
- “不是、不要这单”等否定表达：不调用接口，终结当前目标确认，并提示用户说商品名称或订单号；
- 用户改说另一个商品或订单号：更新待确认目标并再次询问，仍不立即退款；
- 无法唯一识别：列出简短候选摘要，继续等待选择。

成功退款后，只有目标订单变为关闭；同一对话的其他有效订单继续保留。

确认和接口调用需按“对话 ID + 目标订单号”保证幂等。已经进入完成状态的选择再次收到肯定回答时，不得重复调用退款接口。

## 7. 回复约束

业务事件先于回复生成，语言模型只负责把确定状态转换成简短语音话术：

- `order_created` 才能说“订单已下发”；
- `refund_confirmation_requested` 只能询问，不能说“已退单”；
- `order_refunded` 才能说“已处理退单”；
- 调用失败必须明确告知失败；
- 回复中优先播报商品名称和订单号尾号，必要时补充深圳时区的创建时间。

## 8. 事件与兼容性

新增事件名称建议：

- `refund_selection_requested`：多订单场景建立待确认目标；
- `refund_selection_changed`：用户切换目标；
- `refund_selection_cancelled`：用户否认或取消选择；
- `refund_selection_confirmed`：用户确认目标，准备调用接口。

沿用现有 `order_refund_started`、`order_refunded` 和 `order_refund_failed` 记录真实接口结果。后台现有订单和事件列表无需改变合同，只需能展示新增事件。

历史单订单对话保持原行为。历史事件缺少新增选择事件时，不影响有效订单归并。

## 9. 测试设计

自动化测试至少覆盖：

1. 同一对话连续购买可乐和牛奶，两次确认生成两个不同订单号；
2. 第二笔订单只包含牛奶，不重复包含第一笔可乐；
3. 一个有效订单时，明确退单直接退款；
4. 两个有效订单时，通用退单请求默认询问最近订单，且本轮不调用退款接口；
5. 确认默认目标后只退款最近订单，较早订单仍有效；
6. 指定较早订单时仍需二次确认；
7. 同商品多订单默认选择最近一笔，并给出可区分摘要；
8. 否认目标不会调用退款接口；
9. 切换目标后必须再次确认；
10. 服务重启后能够恢复待确认目标；
11. 已退款、已取消和已关闭订单不进入候选；
12. 无有效订单时不调用退款接口；
13. 下单或退款接口失败时不播报成功；
14. “退下”“退出”、裸词“退单/退款”和否定表达不误触发退款。
