# 浏览器全双工拾音与新轮 TTS 接管设计

日期：2026-07-29

## 背景

体验页当前把“播报静音”固定为开启且禁用编辑。TTS 音频进入缓冲后，`canCaptureAudio()` 会同时被 `ttsAsrBlocked`、播放队列、播放器和 TTS 缓冲状态挡住；直到播报结束并经过防回声窗口，浏览器才恢复拾音。

浏览器请求麦克风时已经声明 `echoCancellation: true`，但当前没有读取活动音轨的实际设置，也没有在硬件或浏览器未提供回声消除时区分“已请求”和“已生效”。因此直接开放播报期间拾音会有把扬声器 TTS 再次识别为用户输入的风险。

本次在保留默认硬静音的基础上开放一个受浏览器 AEC 能力保护的全双工模式。用户有效说话时继续走普通 ASR、LLM 和订单分析；旧 TTS 不因 VAD 或 ASR final 立即停止，而是在新一轮 TTS 已达到可播放条件时由新播报接管。

## 目标

- “播报静音”开启时保持现有行为：TTS 期间完全停止向 ASR 发送音频。
- “播报静音”关闭时请求全双工；只有活动麦克风音轨明确报告 `echoCancellation === true` 才实际开放播报期间拾音。
- AEC 未知、未生效或明确为 false 时自动回退硬静音，并在界面展示有效状态。
- 全双工下，上一轮 TTS 播放期间允许用户完成新的普通语音输入。
- 用户开始说话、VAD 断句或收到 ASR final 时不停止旧 TTS。
- 新轮 TTS 达到现有 4096-byte 预缓冲门槛并真正进入可播放队列时，原子地停止旧播报并播放新播报。
- 新轮接管后，旧轮迟到的 TTS 分片不得重新进入缓冲、队列或播放器。
- 订单、退款、会话记录等服务端业务分析继续完成；接管只影响浏览器语音输出。

## 非目标

- 本轮不实现 AudioWorklet、WASM AEC、自研回声消除或音频频谱减法。
- 不承诺所有浏览器、声卡、蓝牙设备都支持可靠双讲；能力以活动音轨实际设置和人工验收为准。
- 不新增服务端“取消 LLM / 取消订单分析”协议。
- 不在检测到用户声音时立即打断播报，也不把普通输入降级为只识别“停一下”的专用通道。
- 不改变设备 SDK 和嵌入式玩偶的拾音策略；本设计只覆盖浏览器体验页。

## 配置与有效模式

### 保存偏好

继续复用服务端字段 `tts_no_interrupt`：

- `true`：用户要求播报静音，实际模式固定为硬静音。
- `false`：用户要求全双工，是否生效仍取决于当前麦克风音轨的 AEC 设置。

体验页不再强制把该字段写成 `true`。加载、切换和快速保存均按真实布尔值同步 `state.recorder.ttsNoInterrupt`、开关和配置请求。

### AEC 能力状态

在 recorder 状态中记录浏览器实际能力，使用三态而不是布尔默认值：

- `unknown`：尚未获得活动音轨，无法执行能力验证。
- `enabled`：活动音轨 `getSettings().echoCancellation === true`。
- `unavailable`：活动音轨明确返回 false，`getSettings()` 缺少该字段，或读取设置失败。

每次 `getUserMedia()` 成功后，从当前 audio track 重新读取设置；音轨结束、停止录音或更换输入设备时回到 `unknown`。请求约束中的 `echoCancellation: true` 只代表请求，不作为生效证据。

### 有效模式判定

有效全双工条件为：

```text
用户关闭播报静音
AND 麦克风处于活动状态
AND 活动音轨 echoCancellation 明确为 true
```

任一条件不满足都使用现有硬静音门控。该判定收敛为一个纯函数，供 `canCaptureAudio()`、状态文案和测试共用，避免 UI 显示全双工但发送路径仍静音，或反之。

## 状态呈现

“播报静音”开关恢复可操作，并在控件内增加一个动态状态文本：

- 开启：`硬静音 · 播报期间暂停拾音`
- 关闭、麦克风未启动：`全双工待验证 · 开始监听后检测回声消除`
- 关闭且 AEC 生效：`全双工已开启 · 回声消除生效`
- 关闭但 AEC 不可用：`已回退硬静音 · 当前设备未启用回声消除`

麦克风主状态继续反映实际可拾音能力。全双工有效且正在播放时显示“播放中，继续监听”；回退状态仍显示“播报中，暂停收音”。状态文案只陈述当前有效状态，不宣称浏览器 AEC 能消除所有环境回声。

## 输入状态机

### 拾音门控

`canCaptureAudio()` 保留权限、录音开关、WebSocket、`pickupAllowed`、发送锁等前置条件。对于播放相关条件采用模式化判断：

- 硬静音：继续要求无 `ttsAsrBlocked`、无恢复窗口、无当前播放器、无排队或缓冲中的 TTS。
- 有效全双工：播放、队列和 TTS 缓冲本身不阻止采集；仍服从发送锁、权限和连接状态。

`beginTtsAsrBlock()` 和 500ms 恢复窗口只对硬静音有效。切换到全双工或确认 AEC 生效时清理遗留的 TTS 拾音锁，但不停止当前播报；从全双工切回硬静音时立即丢弃未完成的录音窗口，防止把切换前后的音频拼成一段发送。

### 发送锁释放

当前文本或音频结束发送后，`sendLocked` 一直保持到 `voice_done`、错误或 `asr_ignored`。这会阻止在旧轮 TTS 播完前形成下一段输入。

全双工模式下，当前输入收到 `asr_final` 后即可解除发送锁，让下一段用户语音开始采集；硬静音继续沿用现有生命周期。释放动作必须由当前会话的 ASR final 触发，并保持 WebSocket 关闭、权限失败、手动停止及错误路径的幂等清理。

本轮不引入多段同时上传：同一时刻仍只有一个活动录音片段。全双工只把下一段允许开始的时点从 `voice_done` 提前到上一段 `asr_final`。

## TTS 轮次与接管

### 轮次纪元

浏览器为当前会话中的 `asr_final` 按到达顺序分配单调递增的本地 epoch，并建立 `turn_id -> epoch` 映射。已有或兼容事件如果没有可映射 `turn_id`，保持当前串行队列行为，不参与跨轮抢占。

会话切换、服务端结束会话和手动新一轮时清空 epoch、胜出轮次与淘汰集合，防止不同 conversation 之间互相接管。

### 可接管时点

新轮不能在以下时点接管旧播报：

- VAD 检测到开始说话；
- 浏览器发送 `audio_stream_end`；
- 收到 `asr_partial` 或 `asr_final`；
- 收到新轮第一个不足预缓冲阈值的 TTS 小包。

接管只发生在一个新轮音频项已经满足同轮 `seq` 排序、并即将从 `queueTtsAudioItem()` 进入全局 `audioQueue` 时。流式 MP3 继续使用 `STREAMING_TTS_PREBUFFER_BYTES = 4096`；非 MediaSource 回退路径在完整 blob 可播放时才具备接管资格。若先收到 `seq=1` 而 `seq=0` 尚未准备好，不提前接管。

### 原子接管步骤

当准备入队项的 epoch 大于当前播放胜出 epoch 时：

1. 把新 epoch 设为当前胜出轮次。
2. 暂停并释放旧轮当前 `Audio`，但保留即将播放的新项。
3. 从全局队列、同轮排序表、MediaSource player 和 blob buffer 中释放所有更旧 epoch 的资源。
4. 将更旧轮次标记为 superseded，后续 TTS chunk 在解码或创建对象 URL 前直接忽略。
5. 将新项放入队列并立即 `drainAudioQueue()`。

清理函数必须支持按 epoch/turn 精确清理，不能复用会清空所有轮次的 `clearTtsPlaybackState()`。资源释放继续保持幂等，每个 object URL 或 stream player 最多释放一次。

### 播放归属

音频队列项增加 `turnId`、`epoch` 和 `seq` 元数据。`currentPlaybackTurnId` 只在 `drainAudioQueue()` 确认某项实际开始播放时更新，不能在任意 `tts_audio_chunk` 到达时更新。

同一胜出轮次的后续 seq 正常连续播放，不触发自我接管。更老轮次的迟到分片被忽略；比当前胜出轮次更新且达到可播放条件的轮次可以再次接管。这样可保证 A 接管 B、C 又接管 A 时，B 或 A 的迟到包都不能夺回播放器。

现有 `interruptedTurnIds` 的显式打断语义继续保留；跨轮接管使用独立的 superseded/epoch 状态，避免把用户显式停止与新轮替换混为一条清理路径。

## 服务端与业务边界

服务端继续按每个输入轮次完成 ASR 后续的 LLM、商品匹配、订单确认、下单和退款分析。浏览器不发送取消旧轮业务任务的消息，也不因新轮接管丢弃旧轮非音频事件。

因此旧轮的 `intent_analysis`、`order_draft`、`order_created` 等仍可更新业务视图；只有 superseded 轮次的 TTS 音频不再播放。若产品后续需要业务级抢占，应另行设计服务端取消协议和订单幂等边界。

## 错误与降级

- 麦克风授权失败：保持现有不可拾音状态，AEC 回到 unknown。
- 音轨 AEC 未明确为 true：自动硬静音，不阻止用户继续使用正常一问一答。
- TTS 元数据、base64、MediaSource 或 Audio 播放失败：继续使用现有终止清理；不得误清除更新轮次已准备的音频。
- WebSocket 关闭、手动停止、会话结束：清空输入锁、epoch、superseded 集合和所有播放资源。
- 播放接管中的 pause/load/revoke 异常：按幂等清理处理，仍应尝试启动新轮，避免旧轮异常阻塞后续播报。

## 文件范围

- `static/index.html`：开放“播报静音”开关并增加有效模式状态节点。
- `static/app.js`：配置同步、AEC 检测、有效模式、输入锁释放、轮次 epoch、定向接管和测试钩子。
- `static/styles.css`：状态文本和回退状态的克制样式，不调整整体页面布局。
- `scripts/voice-integrity-check.mjs`：扩展浏览器状态机验收。
- `docs/接口接入说明.md`：记录浏览器全双工前置条件、回退和接管语义。
- `docs/规划迭代记录.md`：记录实现与验收结果。

服务端 Rust、设备 SDK、嵌入式 `client/` 和订单 MCP 不在本次代码改动范围内；若实现过程中发现浏览器无法在同一 WebSocket 上接受下一段音频，必须先补充协议证据并更新设计，不能静默扩展服务端并发模型。

## 验收策略

### 自动化

在现有 `window.__voiceTest` 和 `npm run voice:check` 基础上增加确定性用例：

- 配置 true 保持硬静音；配置 false 不再被加载/保存逻辑强制改回 true。
- AEC true 时 TTS 播放期间允许普通音频采集，状态显示全双工已开启。
- AEC false、缺失或未获得音轨时回退硬静音，状态与实际门控一致。
- 全双工的 `asr_final` 释放发送锁；硬静音仍保持到现有终止事件。
- 新轮不足 4096 bytes 时旧音频继续播放，不发生 pause/revoke。
- 新轮达到预缓冲且满足 seq 排序后只接管一次，新音频紧接着启动。
- 接管后旧轮迟到 chunk 不创建新 player、buffer、object URL 或 Audio。
- 较旧 epoch 的 TTS 即使晚于新轮到达也不能夺回播放权。
- 同一 turn 的 seq0、seq1 继续按序播放，不触发额外接管。
- 多轮连续接管、空 seq marker、MediaSource 不可用回退、播放拒绝和终止错误均保持资源释放幂等。
- WebSocket 关闭、手动停止和新会话清空轮次状态。
- 现有硬静音、短空 ASR、元数据校验、403 和 UI 三视口回归继续通过。

### 人工浏览器验收

在最新版 Chrome 和 Edge 各执行一次：

1. 开启播报静音，确认播报时麦克风状态为暂停收音。
2. 关闭播报静音并开始监听，确认页面只有在音轨 AEC 明确生效时显示全双工已开启。
3. 仅播放系统 TTS、不说话，确认不会生成新的用户消息。
4. TTS 播放时说完整的新请求，确认旧 TTS 继续到新轮 TTS 可播放时才停止。
5. 确认新轮 TTS 从头播放，旧轮之后到达的音频不再响起。
6. 连续进行三轮双讲，确认最后一轮始终拥有播放权，页面没有重叠音频或卡死状态。
7. 使用不支持或关闭 AEC 的输入设备，确认自动回退硬静音且仍可在播报结束后继续输入。

人工验收需分别覆盖扬声器外放和耳机。耳机可验证状态机，但不能替代扬声器环境下的 far-end-only 与 double-talk 回声测试。

## 完成标准

- 自动化验收全部通过，`git diff --check` 无错误。
- Chrome/Edge 的 far-end-only 不产生误识别，double-talk 能形成新一轮输入。
- 新轮 TTS 只在可播放时接管，旧轮迟到音频无法恢复播放。
- AEC 不可用时页面明确回退，实际发送路径与状态一致。
- 文档准确说明该能力是浏览器 AEC 条件下的全双工，不把请求约束描述为绝对回声消除保证。
